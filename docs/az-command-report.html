az コマンドの現状と、仕様整理の課題

現在の実装は「キャッシュで探す」「Liveで追加取得する」「Webページへ進む」「検索設定を自動更新する」の4種類を、同じプレフィックスにまとめている。最初に整理すべきなのは、キャッシュとLiveの検索範囲・一致条件・順位の違いである。

対象はwaypointのQuick Launch内の az 。認証時に呼ぶAzure CLIの az とは別。仕様書・Rust実装・既存テストを確認した静的調査であり、実アカウントへのAPI問い合わせやGUI操作の実機検証は含まない。

2. 構文と操作のルール

  • プレフィックスは厳密に小文字の az （半角スペース込み）。サブコマンド・属性はASCIIの大文字小文字を区別しない。
  • 属性は先頭から連続している間だけ解釈する。az pr mine active foo は両条件を適用、az pr foo mine は foo mine 全体が検索語。
  • 状態を複数書くと最後が勝つ。関係属性はすべてAND。author reviewer は「作成者またはreviewer」にはならない。
  • live はPR/WIの互換属性。入力だけではAPIを呼ばず、明示操作が必要。
  • 数字のみは部分一致も許す。#ID はID完全一致。PRのID取得は状態条件より番号を優先する。
  • Ctrl+C は選択候補のURL（入力文字列の選択時は通常コピー）、Ctrl+Shift+C はPRのsource branch。
  • APIはバックグラウンドで動く。入力変更後の古い応答は捨てるが、ネットワークリクエスト自体は中断しない。種別ごと同時1件、同一条件の完了後2秒以内は抑止。

4. 整理すべき課題

以下は確認できた挙動・文書不整合と、そこからの設計上の懸念を分けて記載した。変更はまだ実施していない。

優先度 高 / 検索契約

A. Liveは同じ検索の更新になっていない

確認事実: PRはキャッシュの状態省略がall、Liveはactive。ローカルはタイトル・所属・URL・branchを照合するが、PR Liveはタイトル照合。WI Liveは別の全文検索API。横断キャッシュはProjectも含むが横断Liveは3種のみ。

影響: az pr completedのタイトル やRepository名でヒットした候補が、Ctrl+Enter後に消える可能性がある。「最新に更新したら減った」と見える。

推奨: 「キャッシュ検索」と「追加取得」の契約を明記し、状態・検索フィールド・対象種別の差を表にする。まず差を明示する方がAPI負荷を増やさず整理できる。

根拠: src/quick_launch/azure.rs:64、src/quick_launch/search.rs:238、src/quick_launch/azure_search.rs:33、src/azure_devops/sync/pull_requests.rs:150、src/azure_devops/api/work_items.rs:188、src/quick_launch_window/azure_live/mod.rs:265

優先度 高 / 検索の取りこぼし

B. コマンド補完が通常検索を置き換える

確認事実: 単語1つの未知入力はコマンド名へfuzzy照合し、候補があればAzure項目検索へ進まず返す。az pln は補完用の既存テストがある。

影響: コマンド名に似たProject名・タイトルを検索したいとき、検索対象が補完へ切り替わる。引用符などの明示的な回避構文はこのパーサーにない。

推奨: 補完と検索結果を併記するか、補完専用の操作を決める。正式サブコマンド入力と通常検索語の区別を成功例・衝突例で仕様化する。

根拠: src/quick_launch/search.rs:219、src/quick_launch/azure.rs:256、src/quick_launch/tests/search_azure_test.rs:309

優先度 高 / スコープ

C. RepositoryショートカットがRepository限定を保証しない

確認事実: Repository別候補はRepository名を通常の検索語へ挿入する。組織・Project・Repositoryの識別子フィルタは渡さない。review requestsの個人版はneeds-review、Repository版はreviewer。

影響: 同名Repositoryや同じ語を含むタイトルを拾う可能性がある。Liveではタイトル一致なので、対象RepositoryのPRでもタイトルにRepository名がなければ落ちる。

推奨: スコープを限定するショートカットなのか、キーワード入力の省略なのかを先に決める。限定するなら識別子による絞り込みが必要。review requestsの意味も揃える。

根拠: src/quick_launch/azure_entries.rs:49、src/quick_launch/azure_entries.rs:93、src/azure_devops/sync/pull_requests.rs:150

優先度 中 / 構文

D. 属性語と検索語の境界・競合が暗黙

確認事実: 未知語で属性解析を止め、状態属性は最後を採用する。az pr ready はready状態のフィルタになり、「ready」というタイトルの検索にはならない。

推奨: 属性は検索語の前、関係属性はAND、状態は1つという説明と例を追加する。予約語を検索できる区切り構文を設けるかは、別の設計判断として扱う。

根拠: src/quick_launch/azure.rs:134、src/quick_launch/azure.rs:153

優先度 中 / 結果の信頼性

E. 部分失敗と取得上限が結果から分からない

確認事実: Liveは一部Projectが失敗しても、他に結果があればmessageをNoneにする。Pipelineは取得後にfailedを絞り、WIは300件まで。成功候補があると失敗したProjectは主にログで追うことになる。

推奨: 0件を「対象なし」「取得失敗」「取得範囲外」で区別し、部分失敗と上限到達を結果の状態として表す。ページングを追加する前に、有限検索であることを明示する。

根拠: src/azure_devops/sync/work_items.rs:108、src/azure_devops/sync/pull_requests.rs:189、src/azure_devops/sync/pipelines.rs:117、src/azure_devops/api/pipelines.rs:24

優先度 中 / 順位

F. 順位付けの規則が経路ごとに異なる

確認事実: キャッシュはタイトル品質 → 状態/自分との関係 → 一致スコア・使用履歴。PR/Pipeline Liveはタイトル品質 → Project priority → 名前、WIの文字列Liveはpriority → 名前。横断Liveは種別ごとの順に連結する。

推奨: 「自分優先」「Project優先」「関連度優先」の優先順を一覧にする。全経路で統一するか、経路別規則を維持するかを決めてから実装を変える。

根拠: src/quick_launch/azure_search.rs:46、src/azure_devops/sync/pull_requests.rs:180、src/azure_devops/sync/work_items.rs:103、docs/spec.md:216

優先度 中 / 設定変更

G. optimize / suggest / rankは提案ではなく即時保存

確認事実: optimizeはpriorityを振り直し、活動があるProjectの最頻Iterationを1件保存する。成功・失敗はログへ記録。一部Projectの活動取得失敗は0件として扱われ、他で成功すればpriorityの末尾へ回る。全件失敗または活動0件なら保存しない。

影響: suggest/rankという別名でも手動のIteration設定が置き換わる。検索専用コマンド群と同じ位置に設定変更操作がある。

推奨: 自動保存する操作であること、変更対象、部分失敗時の扱いを仕様へまとめる。実行結果の表示と失敗Projectのpriorityを保つかを検討する。

根拠: src/azure_devops/mod.rs:83、src/azure_devops/sync/activity.rs:102、src/azure_devops/sync/activity.rs:134、src/quick_launch/azure_entries.rs:144

5. 仕様整理の進め方

推奨は、まず現在の検索契約を文書で固定し、その後にA〜Cの操作上の不整合を修正する順序。API取得の自動化は、表示50msと明示操作の現行原則を維持して検討する。
  1. 現状を固定: このコマンド表を基に構文・属性・Enter/Ctrl+Enter・取得範囲・順位を分割し、文書の重複を除く。
  2. 先に決める: Liveは同条件の更新か範囲拡大か、補完と検索は併記するか、Repositoryショートカットは厳密限定か。
  3. その後に決める: 部分失敗・上限・鮮度の表示、optimizeの保存結果と部分失敗の扱い。
