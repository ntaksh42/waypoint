# 検索体験全体の高速化

## 目的

Quick Launch のキー入力、初回表示、索引構築、候補更新を計測し、検索結果の品質を
変えずにユーザー操作を塞ぐ処理を除去する。特にトリガーから描画までの 50 ms 予算を
守り、重い I/O や外部連携を UI スレッドへ載せない。

## 現状の根拠

2026-08-30 に以下を実行した。

```powershell
cargo test --release --lib -- --ignored --nocapture bench_
```

実機データでの主な結果は次のとおり。

| 経路 | 実測 |
|---|---:|
| 1 打鍵の同期検索 | 0.033〜0.098 ms |
| 空クエリの区分一覧 | 0.271 ms |
| Azure キャッシュ読取 | 201 ms |
| `Index::refresh_azure` | 158〜213 ms |
| `Index::build` | 168〜448 ms |
| `apps::scan` | 136〜223 ms |

純粋な検索は 50 ms 予算に対して十分小さい。一方、Azure 同期完了通知から呼ばれる
`Index::refresh_azure` は SQLite と共有キャッシュを同期的に読み、UI スレッドを
50 ms を大きく超えて塞ぐ。最初の変更対象はこの経路とする。

## 方針

計測駆動で支配的コストを順に除去する。全面的な索引基盤の置換は行わず、既存の
`Index` と検索結果の契約を維持する。

1. Azure の SQLite 読取と検索候補構築をバックグラウンド側で完了させる。
2. UI スレッドは構築済みスナップショットを短時間で交換するだけにする。
3. 起動、表示直前、候補更新、各検索プレフィックスを再計測する。
4. 次の支配的コストについて、動作を変えない最小の改善を TDD で実装する。
5. 改善が測れない、または複雑さに見合わない変更は採用しない。

## Azure 更新のデータフロー

現状は同期ワーカーがキャッシュを更新した後、`WM_AZURE_DEVOPS_REFRESHED` を送り、
通知を受けた UI スレッドが SQLite を読み直して `Index` を再構築する。

変更後は、同期ワーカー側でキャッシュ更新後に候補を読み、検索用の小文字キーを含む
Azure スナップショットを構築する。通知にはスナップショットを引き渡し、UI 側は
`Index` の Azure 関連フィールドだけを交換する。SQLite、Credential Manager、ネット
ワークへのアクセスは UI スレッドで行わない。

スナップショットは Azure PR / Project と Work Item、および対応する事前計算キーを
一体として扱う。部分的に差し替えて長さや順序の対応を壊さない。

## エラー処理と並行性

- キャッシュ更新またはスナップショット構築が失敗した場合、現在の検索索引を保持する。
- 古い通知が新しい結果を上書きしないよう、既存の同期再入防止と通知順序を確認する。
- ウィンドウ破棄後の通知やポインタ所有権は、既存のバックグラウンド結果通知の作法を
  踏襲する。
- 更新中も現在の候補を検索可能にし、空の中間状態を公開しない。

## 追加調査の範囲

Azure の修正後、以下を同じ release 条件で調査する。

- `Index::build` の内訳と、起動時に同期で必要な処理か
- アプリ、ブラウザ履歴、ブックマーク、favicon の取得回数とスレッド
- Quick Launch 表示直前に重複している索引更新や候補複製
- 通常検索と各プレフィックスの hit / no-hit / 複数語入力
- インクリメンタル入力で前回結果を安全に再利用できるか

ただし、既存ベンチで効果なしと記録された部分ソート、アイコンキー確保の使い回し、
GDI ブラシ共有などは再実装しない。検索結果の一致条件、順位、プレフィックス動作、
空クエリの区分表示は変更しない。

## テストと検証

実装は Red-Green-Refactor で行う。少なくとも次を自動テストで保証する。

- Azure スナップショット交換で Azure 候補だけが更新される。
- apps、bookmarks、history、folders、tabs は保持される。
- 失敗時に現在の Azure 候補が保持される。
- `Entry` と小文字キーの対応が崩れない。
- 検索結果の順序と既存プレフィックスの回帰がない。

完了前に以下を実行する。

```powershell
cargo fmt --all -- --check
cargo test
cargo clippy --all-targets -- -D warnings
cargo build
cargo test --release --lib -- --ignored --nocapture bench_
```

変更前後の同条件ベンチを比較し、改善値と採用しなかった候補を記録する。実機依存の
ベンチが環境要因で失敗または変動した場合は、その事実を明示する。

## 変更境界

最初の変更候補は `src/azure_devops/`、`src/quick_launch/index.rs`、
`src/tray/`、`src/quick_launch_window/` と関連テスト・ベンチである。追加調査で別の
支配的コストが判明した場合も、検索体験の高速化に直接必要な箇所だけを変更する。
新機能、検索仕様の変更、無関係なリファクタリングは行わない。

## 完了条件

- UI スレッド上の Azure キャッシュ読取がなくなる。
- Azure 更新時の UI 側処理が 50 ms 未満であることを実測する。
- 検索体験全体を再計測し、残る支配的コストを評価済みである。
- 効果が確認できた安全な改善を実装し、効果がない案は根拠付きで除外している。
- 全検証コマンドが成功するか、実行不能・既存失敗を明示している。
- 変更をコミットし、`main` へ push してリモート反映を確認する。
